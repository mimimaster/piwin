写文件是怎么回事

1. 先搞清：屏幕后面跑着两个程序

这一页只建立一件事：写文件这件事，不是模型直接改磁盘。

程序 A：Pi 子进程

做什么

  • 跟大模型对话
  • 读文件、搜索代码（这些可以在它自己进程里做）
  • 当模型说「我要写文件」时，它不自己写，而是发请求给程序 B
程序 B：Host（主程序）

做什么

  • 决定能不能写（权限）
  • 真正把内容写到磁盘
  • 记下写前/写后内容，方便你以后点「撤销本轮」
  • 跑 Git、子任务合入父项目等
你在 Desktop 里看到的聊天界面，连的是程序 B（Host）。程序 A（Pi）是 Host 拉起来的子进程，专门跑模型。

模型说「写三个文件」时，实际是：

程序 A 收到模型的三个写文件请求 → 把三个请求发给程序 B → 程序 B 去写磁盘。

2. 写一个文件时，按顺序发生这些事

这一页按时间顺序走一遍。后面说的红卡，出在第 5 步。

1
模型决定：要写某个路径 例如写出工具调用：write_file，路径是 src/a.ts，内容是……
2
程序 A（Pi）收到这个工具调用 它不会在自己进程里打开文件写入。它向 Host 发一条消息：请执行 write_file。
3
程序 B（Host）检查：这个会话还有效吗？这个 Run 还允许写吗？ 无效就直接拒绝。
4
程序 B 做权限检查 可能自动允许，也可能弹窗问你，也可能直接拒绝（比如写到密钥文件）。
5
程序 B 尝试占用「整个项目」的写锁 同一时刻，整个项目只允许一个写操作持有这把锁。拿不到 → 返回 workspace-busy。红卡就在这里产生。
6
拿到锁之后：记下写前内容，再写入磁盘，再记下写后内容 这是为了「本轮撤销」。写完后释放锁。
7
结果返回给程序 A，再给模型 成功就告诉模型写好了；失败就把错误文本给模型（你也会在界面上看到）。

3. 为什么不用 Pi 自带的写文件工具？

不是因为 Pi 写不好。是因为产品规定：改磁盘必须由 Host 做。

以前

早期方案是：模型调用 Pi 自带的 write，但把「真正写磁盘」的函数换成 Host 提供的版本。也就是工具名字还是 Pi 的，落盘仍归 Host。

现在

Pi 子进程里根本不开放 write / edit / bash。模型只能调用 Host 提供的 write_file（以及 delete_file、bash 等）。这些调用一律发回 Host 执行。

原因（直接说）

  • 隔离：如果 Pi 子进程自己写磁盘，权限检查、撤销记录都可能被绕过。
  • 统一：本地 SDK 模式和远程 Worker 模式必须走同一条写文件路径，不能一边用 Pi 的 write、一边用 Host 的 write_file。
  • 撤销：本轮改了哪些文件、写前写后是什么，必须由 Host 记录。Host 自己执行 write_file 最直接。
所以：「Host 能不能接管 Pi？」——写文件这件事，Host 已经在接管。模型不能让 Pi 子进程直接改你的项目文件。

4. 为什么会出现很多 workspace-busy？

因为锁的范围太大，而且拿不到就立刻失败，不会排队等待。

常见场景

模型在一轮里同时请求写 3 个不同文件（这很常见，也正常）。

Host 的规则是：整个项目同时只能有一个写操作。

  • 第 1 个请求拿到锁 → 开始写
  • 第 2、第 3 个请求发现锁被占用 → 立刻失败
Tool error (execution-failed): workspace-busy
如果三个全红

通常不是三个写文件互相抢到一个都不成功。更常见是：当时已经有别的东西占着锁，例如：

  • 同一个批次里的 bash（跑测试、装依赖）
  • 你在界面里做 Git 暂存/提交
  • 子任务正在把结果合回主项目
  • 另一个会话也在写同一个项目
Pi 自己怎么处理的

Pi 自带的 write 用的是：

  • 不同文件：可以同时写
  • 同一个文件：后来的等前面的写完
  • 不会因为「项目里已有别的写操作」就立刻报错给模型

Host 换成 write_file 之后，这套按文件排队没有一起搬过来。

结论：红卡是 Host 当前写锁策略造成的，不是模型乱写，也不是「正常就该满屏红」。

5. 建议怎么改

改 Host 写文件时的锁规则。不要把 Pi 的 write 重新开回子进程。

项目现在建议
写不同文件 也会互撞，后到的失败 允许同时写
写同一个文件 后到的立刻失败 后到的排队，等前一个写完再写
bash 也会占用整项目写锁 不要占用这把写文件锁
撤销本轮 / Git 写操作 / 子任务合入主项目 用整项目锁 继续用整项目锁（这些确实需要互斥）
Pi 子进程里的 write 关闭 继续关闭
最小改动：在 Host 的 write_file / delete_file 上，实现「按文件路径排队」。大约几十行逻辑，和 Pi 现在做的事同类。不要为此去学 Codex 的 apply_patch，也不要重新打开子进程本地写盘。

6. 你只需要记住这些

看完可以合上。以后再看到这套，用下面四句话就够。

1
有两个程序：Pi 跑模型，Host 改磁盘。 模型提出写文件；真正写文件的是 Host。
2
不用 Pi 自带 write，是为了权限、撤销、两种运行模式走同一条路。 不是因为 Pi 写文件能力差。
3
workspace-busy = Host 的整项目写锁被占用，后到的请求立刻失败。 并行写多个不同文件时很容易触发。
4
该改的是 Host：不同文件可并行，同文件排队；bash 不要占写锁。 整项目锁留给撤销、Git、子任务合入。不要把写盘放回 Pi 子进程。
