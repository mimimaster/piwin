## 1. 问题（修订后）

### 用户看到什么

- 普通对话里，同会话换一条提问路线已经好用。
- 项目会话里控件类似，但换路线 / 再生成 / 重试时，**对话上下文与工作区文件是否一致，常常说不清**。
- 会话树、新开会话、Git 工作区三类入口都像「分叉」，容易混。

### 真正的缺口（按优先级）

1. **首要：** 所有探索入口（切换已有路线、编辑历史再发、开分支、失败重试、成功后再生成）对「当前文件状态」的解释与保护不一致；最容易误导。
2. **其次：** 树导航能力不足（目前主要是分叉点列表，不能安全地「预览 / 从某轮继续」）。
3. **再次：** 并行改代码缺少稳妥的独立工作区入口（应是关联新会话 + 固定目录，而不是第一版就让同一会话随路线换目录）。
4. **待验证：** 热切换时是否值得接入 Pi 完整导航（不是「没调用 `branch()` 就等于做错了」；先有性能与保真数据再投入）。

### 成功标准（修订）

1. 每个探索入口都能让用户理解：对话变了什么、文件会不会变、会不会丢掉已执行过的副作用。
2. 失败重试不假装「什么都没发生过」；已发生的写入可追溯。
3. 需要并行试方案时，能从明确提交创建「关联新会话 + 独立工作目录」。
4. 可浏览整棵对话树；在安全轮边界明确「从此继续」；预览不打断其他客户端。
5. 无论冷热激活，继续执行遵守同一套路径 / 压缩 / 附件 / 工具配对规则；退化可观察；切换延迟可接受。
   （可用热导航实现，但不是唯一实现。）

---

## 2. 仍然成立的分层

```
对话路线     管历史与模型上下文
工作副本     管仓库文件隔离（关联会话 + 固定目录）
文件撤销     管可验证的本轮/尝试级文件恢复（独立能力）
```

后台进程、外部服务、权限不随「对话指针」自动恢复。

---

## 3. 落地顺序（修订）

| 阶段 | 用户结果 | 要点 |
|------|----------|------|
| **加强版 P0** | 每个探索入口都解释并保护文件状态；失败记录不掩盖已执行动作 | 统一「路线转换」计算；覆盖编辑分支 / 切换 / 重试 / 再生成；校准可在 Host 重启后恢复；取消不改变当前路线 |
| **简化版 P3** | 从明确 Git 提交创建关联会话 + worktree，A/B 可分别跑 | 源目录不变；新目录起点可验证；失败清理与显式保留；不在同一 sessionId 内换 cwd |
| **收敛版 P1** | 可查整棵对话树；在用户轮或完成助手轮边界明确继续 | 预览不移动共享执行叶子；revision 冲突需刷新；工具节点先只读定位 |
| **有门槛的 P2** | 有实测收益时减少 runtime 重建 | 封装完整导航契约（非裸 `branch()`）；SDK/RPC 同矩阵；映射按 `runtimeGenerationId`；失败则失效重建 |

若近期最强反馈是「找不到旧回复」而非并行改代码，可交换「简化版 P3」与「收敛版 P1」。

**若只做两阶段：加强版 P0 + 简化版 P3。** 并明确：完整节点导航尚未交付。

---

## 4. 加强版 P0（第一刀详细范围）

### 必须统一的入口

| 入口 | 要求 |
|------|------|
| 切到已有兄弟路线 | 沿用并加强：写操作确认 + 可恢复的待校准 |
| 编辑历史提问 / 开分支再发送 | **补齐**与切换相同的写操作确认与校准（当前 rebase 路径缺失） |
| 失败重试 | 可确认；不删除唯一执行证据；区分已完成动作与未闭合工具 |
| 项目成功轮「重新生成」 | 默认关闭入口；底层规则仍与探索路径一致 |

### Host 统一「路线转换」

一次计算并持久化：

- 源路径、目标路径
- 被离开的执行记录与观察到的写操作
- 当前工作区事实（写入已观察 / 未观察 / 信息不足）
- 是否需要用户确认
- 待注入的校准内容（重启后仍在，注入成功后才消费）

### 写入判定

区分「已观察到写入」「未观察到写入」「信息不足」。
General 会话也可能有副作用，不能只靠「是不是 Conversation」当无副作用保证。

### 现成能力边界（写进实现说明）

- 切换前文件列表：确认框已有 → P0 是统一覆盖与解释，不是从零 invent。
- 「先暂存再切换」：客户端 stash，未与路线绑定，不是路线级文件版本。
- 文件撤销：已有 turn-changes 基础，需盘点复用，不假定已完整交付。

---

## 5. 简化版 P3（独立探索）

- 形态：**关联的新会话 + 固定 worktree + 明确 baseCommit**（首选干净提交）。
- 源会话保留原路线；新会话带历史前缀与来源链接。
- 复用现有 Fork / lineage，不新建顶层任务域，不复用 subagent 父子关系。
- 不提供「恢复到某条历史消息当时未提交文件」——除非已有可验证检查点。
- 隔离的是仓库工作文件，不包含任意外部副作用或 OS 权限。

---

## 6. 收敛版 P1（浏览与继续）

- 需要新的 Host 导航语义与有界树查询；不能只改 UI 复用现有 `switchActiveBranch`（它会跳到子树最新叶子）。
- **预览：** 本地选择，不移动共享执行叶子。
- **编辑提问：** 先本地草稿；发送时 Host 原子创建新路线。
- **从此继续：** 提交目标节点 + 预期 revision；无运行冲突才改共享路径。
- 初期只允许完整用户轮或已完成助手轮；工具节点先查看定位。

---

## 7. 有门槛的 P2（热导航）

- 先测量：现有切换 + 下次激活的耗时、内存、回放保真缺口。无收益则不主线投入。
- 若做：`agent-host` 封装与 Pi 对齐的**完整导航入口**（运行检查、摘要、扩展钩子、重建 Agent 消息），禁止只拨 `SessionManager.branch()` 指针。
- 产品节点 ↔ 原生条目是「区间与可继续位置」，不是简单一对一表。
- 映射按 Host `runtimeGenerationId` 管理。
- 任一步失败：禁止 prompt，runtime 失效，从产品权威重建。

---

## 8. 作者采纳声明

同意评审对原案的主要修正：

1. 首要缺口是「入口级上下文与文件状态可解释」，不是「必须调用 Pi.branch」。
2. P0 必须覆盖编辑分支与重试，不能只谈已有切换。
3. 独立探索第一版用关联会话 + 固定 worktree，不在同一会话内随路线换目录。
4. 顺序改为加强 P0 → 简化 P3 → 收敛 P1 → 有门槛 P2。

待产品负责人确认后，从加强版 P0 开工。
