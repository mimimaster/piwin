第二轮调研 · 以 Pi 会话树为参照

项目会话里的「树」，
应该怎么做

上一版建议只盯着「改文案、藏按钮」，确实浅了。这次对照的是 Pi 自己的会话树（/tree），以及 piwin 现在实际怎么接 Pi。下面用普通话说清楚：Pi 是什么、我们差在哪、项目会话该怎么分阶段做。

先纠正一个误会。 Pi 的会话树也不会在切换分支时把磁盘文件改回去。它管的是「对话记忆往哪长」；文件列表只是告诉模型「你离开的那条路改过哪些文件」。 所以正确目标不是「做成会回滚磁盘的树」，而是：把 Pi 那种在同一条会话里试另一条路的能力，完整接到项目工作上——包括上下文怎么切、离开旧路时怎么交代、以及（另外一层）要不要给新路单独工作区。

一、Pi 的会话树到底是什么

依据已安装的 @earendil-works/pi-coding-agent@0.84.2 文档（docs/sessions.md、session-format.md、compaction.md）和 SessionManager 接口。

Pi 把一整场会话存成一棵树（JSONL 文件）。每条记录有父亲；当前站在哪条路上，由「叶子指针」决定。历史只追加、不改写、不删除。

你: 帮我改登录
 └─ 助手: 方案 A …
     ├─ 你: 继续做 A …     ← 当前叶子
     │   └─ 助手: …
     └─ 你: 改做方案 B …   ← 另一条兄弟路
         └─ 助手: …
Pi 里的动作普通含义
/tree 在同一场会话里跳到任意历史节点，从那里继续。不新开文件。
在树里点一条「用户消息」 叶子退到它的上一条；编辑器填回那句话；你改完再发 = 开出一条新兄弟路。
在树里点助手 / 工具结果 叶子移到那里，从该点接着聊。
离开旧路时的「分支摘要」 可选：让模型总结你刚离开的那条路，并记下对话里出现过的读写文件清单，塞进新路的上下文。不回滚磁盘。
/fork / /clone 另存成新的会话文件（新开一场），不是同文件里切叶子。

一句话：Pi 的树 = 同一会话文件里的多条对话路线 + 可选「离开时交代一下」。 它不是 Git，也不是文件时光机。

二、piwin 现在实际怎么做（对照 Pi）

已经像 Pi 的部分

  • 产品库里也有父子关系，能分叉、能切回。
  • 改提问再发 = 开兄弟路（接近 Pi 点用户消息再编辑）。
  • 切走时若写过文件会警告，并在下一轮提示里塞文件清单 + git 快照（接近「分支摘要」的意图，但是 Host 写的，不是 Pi 的 LLM 摘要）。
  • 普通对话里这套已经好用。

和 Pi 差得很远的部分

  • 界面只是「分叉点列表」，不是 Pi 那种能点进工具步骤、助手节点的完整树。
  • 每次切叶子：把正在跑的 Pi 整场扔掉，再按当前路线性重放进一块空白内存。Pi 自带的 branch() 根本没用上。
  • 没有「离开旧路时要不要摘要」的交互。
  • 没有标签书签、没有从任意助手节点接着干的完整导航。
  • 项目里文件仍共享一份工作区——Pi 也是这样，但 Pi 至少会用分支摘要把「旧路改过啥」说清楚。
技术事实（给自己对齐）： createSeededPiSessionManager 只用 SessionManager.inMemory()，按活跃路径 appendMessage。 从不调用 branch / branchWithSummary / getTree，也不打开 Pi 的 JSONL 文件。 所以：**产品侧有树，Pi 运行时永远是一条直线。**

这就是为什么「只改文案」不够： 普通对话不依赖完整树也能爽； 写代码的项目会话，需要的是 Pi 那种「在同一场里换路线、换上下文、离开时交代文件」的工作方式，而不只是顶栏多一个列表。

三、三条可选路线

路线 A — 继续只用产品库的树，但把体验对齐 Pi 的 /tree

做什么：不接 Pi 的会话文件。界面和流程向 Pi 靠：完整路径树、点用户消息=编辑再发、点助手=从那里继续、切走时可选「摘要旧路」、文件警告保留。

优点：不碰「恢复 Pi 会话文件会静默出错」的老风险；改动集中在产品层。

缺点：每次切换仍要拆掉 Pi、重放一整路，又慢又容易丢「只活在内存里」的中间状态。

路线 B — 产品库仍是权威，但热会话里让 Pi 真正用树

做什么：会话还在内存时，切叶子调用 Pi 的 branch()（必要时 branchWithSummary），不要每次拆掉重播。进程挂了再按产品库重放。

优点：认真用上 Pi 的树能力；冷启动仍走产品库，不赌「恢复 Pi 文件」。

缺点：要维护「产品消息 id ↔ Pi 条目 id」的映射，做不好会两边不一致。

路线 C — 探索时绑定独立工作区（和 Pi 树正交，但项目必需）

做什么：「换方案」时可选：仍用当前目录，或开一份独立工作副本（git worktree），并和这条对话路线绑在一起。切换对话路线时，若绑了工作副本，就一起切过去。

优点：解决「对话换了、代码还是上一方案」——这是写代码场景的真痛点。Pi 自己也不解决磁盘，必须产品补这一层。

缺点：工作副本有成本（依赖、环境）；不能默认每次改提问都开一份。

不推荐当默认的：直接拿 Pi 的 JSONL 当产品真相

可以以后做技术试验，但不应先押宝。历史判断是：直接恢复 Pi 会话文件，看起来像恢复了，工具/进程状态可能已经不对，而且双模式（SDK/RPC）没验证过。产品记录仍应在 ~/.piwin。

四、推荐方案（项目会话）

推荐：路线 B + 路线 C，分阶段做；路线 A 的体验目标并进。
普通对话可以继续用现在的轻量分叉。 项目会话要对齐 Pi 的工作方式：同一场里换路线、离开时交代、需要隔离时才给独立工作区。

用户最终应感受到什么（项目）

  1. 1 同一条项目会话里试另一条实现路线——像 Pi 的 /tree，不是动不动新开一场聊天。
  2. 2 从任意一问一答跳回去再改——点提问可改写重发；点某次助手结果可从那里接着干。
  3. 3 离开旧路时被问一句：要不要总结旧路（含改过哪些文件）——对齐 Pi 的分支摘要；同时保留现在的磁盘警告。
  4. 4 旧路已经大改文件时，明确提供「用独立工作区开这条新路」——默认不要静默隔离；用户点了才开。
  5. 5 失败重试 ≠ 开新路线——挂了就原地再跑；不要和「换方案」混成一个按钮。

分阶段落地

阶段交付目的
P0 · 行为对齐 项目里把「重新生成」从「换方案」里拆开（失败用重试；换方案走编辑/开分支）。 顶栏/空态写清：分叉的是对话路线。 切走时提供可选「摘要旧路」（先用现成文件清单 + git 快照，再迭代成真正的模型摘要）。 先让项目会话的手势和 Pi 一致，不再误导。
P1 · 完整树导航 会话树从「分叉点列表」升级到接近 Pi 的路径树：能看到关键助手节点，能跳到节点继续。 （仍以产品库为权威。） 补上 Pi /tree 里「点哪里就从哪里继续」的能力。
P2 · 热切换用 Pi.branch 会话仍活着时，切叶子走 SessionManager.branch，避免整场拆掉重放。 进程死后仍从产品库恢复。 认真接上 Pi 运行时的树，而不是只仿一个 UI。
P3 · 可选独立工作区 「开新路线」在写过文件时可绑 git worktree；切换路线时若已绑定则一起切换。 与现有 Git 芯片打通，但入口在「探索」手势上。 补上 Pi 不管的磁盘隔离。
试验轨 Pi JSONL 是否可作辅助存储：单独打样，证明杀进程恢复无静默错误后再谈。 不阻塞上面四步。

五、和「只改文案」那版有什么不同

上一版

假定产品树已经够了，项目只要少骗人。

建议停在：藏重新生成、改副标题。

这一版

以 Pi 的 /tree 为产品参照：同场换路、节点导航、离开时摘要、（另层）可选工作区。

承认：现在只是「产品库有树 + Pi 每次重放直线」，项目场景不够。

六、建议你怎么拍板

若同意推荐，请确认这三句话：

  1. 项目会话的树，要对齐 Pi 的「同场换路线」，不是只对齐普通聊天的「换个说法」。
  2. 磁盘隔离是附加层（P3），不是树的定义；但项目探索在「已写文件」时应能一键要隔离。
  3. 先做 P0→P1→P2；Pi 会话文件当真相留给试验，不挡主线。

确认后，下一刀可以从 P0 开工（行为拆分 + 离开旧路的交代），同时开 P1 的树导航设计。

主要依据：Pi docs/sessions.md（Branching with /tree）、docs/compaction.md（Branch Summarization）、 SessionManager.branch / branchWithSummary / getTree； piwin packages/agent-host/src/seeded-pi-session.ts（仅 inMemory 线性重放）； 以及产品侧会话树切换时拆掉 live 会话再按路径重放的实现。
