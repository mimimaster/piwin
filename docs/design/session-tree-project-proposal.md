## 1. 问题是什么（请先评这一段）

### 1.1 用户可感知的现象

1. **普通对话（Conversation）里，会话树已经好用。**
   用户改一句历史提问再发送，同一条会话里会出现另一条路线；气泡旁有「第几版 / 共几版」可切换；顶栏有「会话树」可浏览分叉。主聊天区始终只显示当前这一条路线。

2. **项目会话里，控件看起来差不多，但体验不对。**
   项目会话也会改代码、写文件。用户换一条对话路线时，聊天记录变了，工作区文件通常不会跟着回到「那条路线对应的状态」。若再点「重新生成」，对话可能多出一版回答，文件仍停在上一版尝试留下的改动上。用户容易以为「切对话 = 撤销改文件」，实际不是。

3. **项目里还有另外两套也像「分叉」的入口，容易混。**
   - 会话树 / 版本切换：仍在**同一条会话**里换对话路线
   - 「从这里分叉」：另开一条**新会话**（默认仍共享同一工作区）
   - Git 分支芯片：换代码分支或另一份工作目录，可能再开一条项目会话

### 1.2 真正要解决的问题（技术表述）

问题不是「项目会话有没有会话树」。
**产品库里已经有分叉与切换；Host 对普通对话和项目会话用同一套分支命令。**

真正的缺口是两层：

**A. 与 Pi 原生会话树的能力落差**
Pi 把一场会话本身建成树：可在同一会话文件内跳到任意历史节点继续；离开旧路线时可对旧路做摘要（含对话中记录到的文件读写清单）。
piwin 目前只在**产品转录库**里维护分叉，接到 Pi 时却是：切路线 → 拆掉当前 Pi 运行时 → 把当前路线线性重放进一块空白内存。
也就是说：**产品侧有树，Pi 运行时始终被当成一条直线用。**

**B. 写代码场景下「对话路线」与「工作区文件」未正确分层**
Pi 自己的 `/tree` **也不会**在切树时回滚磁盘。
写代码时若只模仿聊天分叉、不补「离开旧路时的交代」和「可选的独立工作区」，项目会话就会比普通对话更容易误导。

### 1.3 成功标准（评阅时可拿来打分）

方案成立，当且仅当同时满足：

1. 项目用户能在**同一条会话**里尝试另一条实现路线，并切回旧路线看对话。
2. 用户不会误以为「切换对话路线 = 文件自动恢复」。
3. 「失败重试」与「换方案探索」在交互上分开。
4. 中长期能用上 Pi 的切树能力（同场换路线、离开时摘要），而不是永远拆掉重放。
5. 需要真正并行改同一仓库时，有明确的「独立工作区」入口；该入口不是会话树的默认真相。

## 2. 参照物：Pi 原生会话树（必须理解）

来源：Pi 官方 `sessions.md` / `session-format.md` / `compaction.md`，以及 `SessionManager` 公开 API。

### 2.1 模型

- 一场会话 = 一个 JSONL 文件（或内存中的同等结构）。
- 每条记录有 `id` 与 `parentId`，形成树。
- 「当前站在哪」由叶子指针决定；新消息挂在当前叶子下。
- 历史只追加，不改写、不删除。
- 送给模型的上下文 = **从当前叶子走回根的那一条路径**，不是整棵树。

### 2.2 用户动作

| Pi 动作 | 含义 |
|---------|------|
| `/tree` | 在**同一会话文件**内跳到任意历史节点，从那里继续 |
| 在树里选中一条用户消息 | 叶子退到其父节点；编辑器填回该提问；改完再发 = 开出兄弟路线 |
| 在树里选中助手 / 工具结果等 | 叶子移到该节点，从该点继续 |
| 离开旧路时的分支摘要（可选） | 总结被离开的那条路，并带上对话中追踪到的读写文件清单，注入新路上下文。**不回滚磁盘** |
| `/fork` / `/clone` | 另存为**新的会话文件** |

### 2.3 Pi 不管什么

- 切换树节点时，**默认不恢复工作区文件**。
- 不负责 Git worktree / 并行隔离（那是另一类能力；可用扩展做检查点，但不是核心语义）。

**评阅要点：** 若方案把「会话树」定义成「文件时光机」，就与 Pi 也不一致。

## 3. piwin 现状（代码事实，不谈口号）

### 3.1 已经有的

- 产品转录（SQLite）里有父子关系与当前活跃叶子。
- 桌面端：顶栏「会话树」、气泡旁版本切换、编辑后「发送新版本 / 开分支 / 重试」。
- 切换时若被离开的路线写过工作区文件：弹确认（继续切换 / 先暂存再切换 / 取消）；下一轮可注入文件清单与 git 快照。
- 普通对话里，上述「改提问 → 新版本 → 切换回来」已经顺手。
- 普通对话与项目会话：**同一套 Host 分支能力**；不是项目没做树。

### 3.2 关键缺陷

1. **接 Pi 的方式是线性重放，不是切树。**
   `createSeededPiSessionManager` 使用 `SessionManager.inMemory()`，按活跃路径依次 `appendMessage`。
   不调用 `branch` / `branchWithSummary` / `getTree`，也不把产品会话绑到 Pi 的 JSONL 文件上。
   切换路线时常见路径是：结束当前 live 会话 → 改产品叶子 → 下次再按新路径重放。

2. **界面是「分叉点列表」，不是 Pi 那种完整树导航。**
   难以等价实现「点到某次助手/工具节点再继续」的完整 `/tree` 体验。

3. **项目里「重新生成」仍可能挂在最新助手气泡上。**
   实现上只要存在重试回调就会提供；未按「是否项目会话」关掉。
   在已改文件的成功工具轮上，「再生成一版并保留旧回答」会放大「对话变了、磁盘没变」的错觉。

4. **三个入口语义不同，文案都像分叉。**
   同场换路线 / 新开会话 / Git 工作区切换，用户难区分。

### 3.3 刻意不做的事（现状约束）

历史上选择**不把 Pi 的 JSONL 当作产品恢复真相**，原因包括：恢复后可能「看起来像恢复了」，但工具/进程状态并不等于当时；且 SDK/RPC 双模式未证明可安全共用同一套 JSONL 恢复。
产品权威在 `~/.piwin` 的转录库；Pi 被当作可丢弃的执行引擎，按当前路径喂进去。

## 4. 方案总览（推荐）

### 4.1 一句话

**项目会话的会话树，应对齐 Pi 的「同场换路线」工作方式；磁盘隔离与文件撤销是另外两层，按需叠加，不要伪装成会话树本身。**

### 4.2 分层模型（评阅核心）

```
第 1 层  对话路线树（对齐 Pi /tree）
         同一会话内多条路线；切换 = 换模型上下文路径；可选「离开旧路摘要」

第 2 层  工作区策略（Pi 不管，项目必须补）
         默认共享当前目录；当旧路已写文件且用户要并行探索时，可选独立工作副本

第 3 层  文件撤销（可选、独立产品）
         「撤销本轮助手改过的文件」；不是切会话树，也不是 Git 历史的完整替代
```

普通对话主要用第 1 层即可。
项目会话第 1 层必须做完整；第 2 层在「已写文件还要换方案」时变为显式选项；第 3 层可后置。

### 4.3 明确不采用的默认方案

| 不采用 | 原因 |
|--------|------|
| 只改文案、藏一个按钮就结案 | 未解决「Pi 侧永远直线重放」与「项目探索缺完整同场换路」 |
| 默认每次分叉都开独立工作区 | 成本高；Pi 也不是这个默认 |
| 把切会话树做成自动 `git checkout` / 文件回滚 | 与 Pi 不一致，且与「一份脏工作区里协作」冲突 |
| 立刻让 Pi JSONL 成为产品唯一真相 | 恢复静默错误风险高；应单独立项试验，不挡主线 |

## 5. 详细方案（分阶段）

### 阶段 P0 — 行为对齐（小、可立刻做）

**目标：** 项目会话里，手势先和 Pi 的语义对齐，去掉最误导的混用。

1. **拆开两种动作**
   - **重试：** 同一提问、同一路线，再跑一次（典型：失败后）。不保留「成功工具轮的旧回答兄弟」作为默认探索手段。
   - **换方案：** 编辑提问后「发送新版本」，或明确「开分支」。

2. **项目会话下，最新成功回答上的「重新生成」不再作为默认探索入口。**
   （若产品坚持保留，必须文案写明：只换回答，不撤销已改文件——但推荐直接拿掉，避免双语义。）

3. **顶栏 / 空态说清一句人话：**
   「这里切换的是对话路线，不会自动把工作区文件改回去。」

4. **离开旧路时的交代（先用现成能力）：**
   已有「写过文件则确认」+「下一轮注入文件清单 / git 快照」。
   P0 把它提升为用户可理解的一步：切换前能看见「旧路动过哪些文件」，而不是只有技术校准。

**验收：**
项目用户完成「改提问开新路 → 切回旧路看对话」时，不会在 UI 上被引导去点「重新生成」当换方案；切换前能意识到文件不会自动恢复。

---

### 阶段 P1 — 完整树导航（对齐 Pi `/tree` 的交互面）

**目标：** 会话树从「分叉点列表」升级为「可导航的路径树」。

1. 能展示当前会话中与探索相关的关键节点（至少：用户提问、助手回复；理想含可定位的重要工具结果摘要）。
2. **选中用户提问：** 进入编辑并允许发送新版本（= 开兄弟路），对齐 Pi。
3. **选中某次助手回复：** 将当前路线切到该点，允许继续提问。
4. 主聊天区仍只渲染当前活跃路线（与现在一致）。

**权威仍在产品转录库。** 本阶段仍可不调用 Pi 的 `branch()`。

**验收：**
用户无需只靠「分叉点列表」，能从树里跳到某一问或某一答再继续，行为接近 Pi `/tree` 的选择规则。

---

### 阶段 P2 — 热会话使用 Pi 的切树（对齐 Pi 运行时）

**目标：** 会话进程仍存活时，切换路线调用 Pi `SessionManager.branch`（需要时 `branchWithSummary`），避免每次拆掉整场再线性重放。

1. 产品库仍是对外权威（列表、多端、恢复入口）。
2. 热路径：产品切叶子 ↔ Pi 切叶子（维护稳定的 id 映射）。
3. 冷启动 / 进程死后：仍按产品库活跃路径重放（或更完整的重建），不依赖「恢复 Pi JSONL 当真相」。
4. 「离开旧路摘要」逐步从「Host 文件清单」升级到可选的模型摘要（语义对齐 Pi `branch_summary`），并继续叠加磁盘真相（git 快照）。

**风险：** 产品树与 Pi 树映射漂移。
**缓解：** 映射单测 + 切换后上下文一致性检查；漂移则回退到线性重放。

**验收：**
同一次桌面进程内，连续多次切换路线，不必每次完整冷激活；模型上下文与当前产品活跃路线一致。

---

### 阶段 P3 — 可选独立工作区（补上 Pi 不管的磁盘层）

**目标：** 当旧路已经大改文件、用户要并行试新方案时，提供明确隔离，而不是假装会话树会回滚文件。

1. 「开新路线」在检测到旧路写过文件时，提供选项：
   - 仍用当前工作区（保持现状 + 警告）；或
   - 使用独立工作副本（git worktree），并与该对话路线绑定。
2. 若某路线已绑定工作副本：切换该对话路线时，一并切换工作目录（或引导「去那里工作」）。
3. 默认不要每次改提问都自动开工作副本。
4. 与现有 Git 芯片能力打通，但**入口挂在「探索」上**，避免三个入口抢同一套话术。

**验收：**
用户能完成「方案 A 已改一堆文件 → 方案 B 在干净/独立目录试 → 对话与目录一起切换」；共享工作区路径仍然可选且警告清楚。

---

### 试验轨 — Pi JSONL 是否可作辅助存储

单独打样：在 Host 管控的路径下打开/恢复 Pi 会话文件，验证杀进程后叶子与工具相关状态是否会静默出错。
**未通过前，不得让 JSONL 成为产品唯一真相。** 不阻塞 P0–P3。

## 6. 普通对话 vs 项目会话（方案下的差异）

| | 普通对话 | 项目会话 |
|--|----------|----------|
| 第 1 层同场换路线 | 需要，现已基本够用 | 需要，且要补到接近 Pi `/tree` |
| 离开旧路摘要 / 文件交代 | 少见 | 重要 |
| 「重新生成」当探索 | 可接受（几乎不写盘） | 不作为默认探索 |
| 独立工作区 | 通常不需要 | 旧路已写文件且要并行时需要可选 |
| Git 芯片 | 无 | 有；与会话树分工明确 |

## 7. 与旧建议的关系（供评阅）

曾有一版建议：项目会话「只需关掉重新生成 + 改文案」。

该建议**作为 P0 的子集仍然成立**，但**作为完整方案不成立**，因为它：

- 未解释 Pi 会话树的真实语义；
- 未处理「产品有树、Pi 直线重放」的结构性落差；
- 未给出项目场景下完整同场换路与可选工作区的分层。

本文件以 Pi 为参照重写了完整方案；P0 可先做，但不宣称「做完 P0 就等于解决项目会话树」。

## 8. 请第三方模型评阅的问题清单

请直接回答：

1. **问题定义是否准确？** 是否同意核心缺口是「A 与 Pi 能力落差 + B 对话/磁盘分层」而不是「项目没有树」？
2. **以 Pi `/tree` 为参照是否合理？** 有无重大误读（尤其是：Pi 切树是否回滚文件）？
3. **三层模型（对话树 / 工作区策略 / 文件撤销）是否清晰、有无应合并或拆分？**
4. **阶段顺序 P0→P1→P2→P3 是否合理？** 是否应把 P3（工作区）提前到 P2（Pi.branch）之前或之后？
5. **最大风险是哪一步？** 映射漂移、工作区绑定、还是产品复杂度？
6. **若只能做两个阶段，应保留哪两个？**
7. **有无更优替代方案？** 例如：项目会话放弃同场树、全部改为「新会话 + 工作区」？请说明代价。

## 9. 推荐结论（作者立场，供反驳）

1. 普通对话的会话树可以基本保持现状。
2. 项目会话应对齐 Pi：同场换路线、节点导航、离开时交代；而不是只对齐「聊天换措辞」。
3. 热路径应逐步使用 Pi 的 `branch`，而不是永远拆掉重放。
4. 磁盘隔离是显式可选项，挂在探索上；不是会话树的默认含义。
5. Pi JSONL 当产品真相：只试验，不主线。

**作者建议的落地顺序：P0 → P1 → P2 → P3；试验轨并行。**
