# Image generation call flow v3

## Status

Implemented in the image-generation vertical slice that accompanies this spec.

## Problem

The existing `image_gen` path had the right package boundaries, but its runtime
contract was too loose:

- an explicit model id, or the chat default, could select a model that was not
  configured for image generation;
- the provider response was reduced to the first byte array, so multi-image
  responses were silently truncated;
- generated bytes were always labelled and saved as PNG, even when the provider
  returned JPEG or WebP;
- provider custom headers were not sent and HTTP failures discarded the useful
  provider error message;
- Settings could save route metadata, but could not exercise the real image
  endpoint before the user tried it in a conversation.

## Goals

1. Keep one configuration source under `PiwinConfig.providers` plus
   `PiwinConfig.imageGeneration.defaultModel`.
2. Make image model selection deterministic and capability-aware.
3. Normalize OpenAI-compatible and Google Imagen responses into one internal
   batch result before media persistence.
4. Persist every returned image with a MIME type derived from its bytes.
5. Provide a Settings smoke test that calls the same provider adapter as the
   agent tool without adding the test image to a session.
6. Preserve the existing `image_gen` tool name, permission action, media-store
   boundary, and Desktop/CLI parity.

## Configuration model

An image model is configured on a provider as a normal `ModelConfigEntry`:

```json
{
  "id": "gpt-image-2",
  "capabilities": ["image-generation"],
  "routes": {
    "image-generation": {
      "path": "/images/generations",
      "timeoutMs": 180000
    }
  }
}
```

The route path is optional. Host defaults remain protocol-aware:

- `openai-compatible`: `POST {baseUrl}/images/generations`
- `google-gemini`: `POST {baseUrl}/models/{modelId}:predict`
- `anthropic-compatible`: unsupported with a configuration error

`imageGeneration.defaultModel` is the only image default. Chat defaults are no
longer accepted as an arbitrary fallback. If no image default exists and there
is exactly one enabled image model, Host may use it as a migration convenience;
if several exist, Settings must choose a default.

For compatibility, an existing model with an image-generation route is treated
as image-capable even if its capability tag predates this spec. Any model saved
through the current Settings UI receives the explicit capability tag.

## Runtime flow

```text
image_gen arguments
  -> resolve enabled image provider/model
  -> resolve secret + provider headers
  -> protocol adapter request (abort + route timeout)
  -> normalized GeneratedImage[]
       bytes + sniffed mimeType + optional revisedPrompt
  -> preflight media allow-list
  -> save every item through @piwin/media
  -> ToolResult paths + per-image metadata + MediaAttachmentRef[]
  -> transcript/Desktop attachment rendering
```

The tool accepts an optional provider id in addition to a model id. This removes
ambiguity when two configured providers expose the same model id. A bare model
id is accepted only when it resolves to one enabled image model.

The requested image count is an integer from 1 through 4. The adapter accepts a
provider returning fewer items and reports the actual count; it never duplicates
or invents outputs.

## Provider normalization

OpenAI-compatible responses support every item in `data[]` using either
`b64_json` or an HTTP(S) `url`. Google Imagen responses support every item in
`predictions[]` using `bytesBase64Encoded`. Data URLs are decoded locally.

Supported persisted raster formats are PNG, JPEG, WebP, and GIF. Magic bytes
take precedence over a provider-declared MIME type. Unknown or non-image bytes
are rejected rather than written with a false extension.

Provider HTTP errors include a bounded, sanitized provider message when one is
available. API keys and authorization values are never included in the error.

## Settings smoke test

`models/image-test` accepts a provider and model id, resolves the same stored or
one-shot secret used by other model operations, and invokes the same normalized
adapter with one small deterministic prompt. It returns only duration, count,
MIME types, and byte sizes. Bytes are discarded and no session/media record is
created.

## Acceptance checks

- A non-image chat default cannot make `image_gen` appear or receive a request.
- A stale image default produces a clear configuration error.
- Duplicate model ids require an explicit provider id.
- Multi-image provider responses produce the same number of media attachments.
- JPEG bytes are saved as `.jpg` with `image/jpeg`; equivalent checks cover PNG,
  WebP, and GIF detection.
- Custom provider headers are present on generation requests.
- Settings can test a configured image model through `models/image-test`.
- Host Runtime typecheck and touched tests pass.
- A real configured provider smoke test verifies the persisted extension and
  MIME type without modifying the user's configuration.

## Non-goals

- Image editing/inpainting and reference-image multipart upload.
- Provider-specific advanced controls beyond prompt, size/aspect, quality, and
  count.
- Changing Pi ownership, permissions, Gateway behavior, or media-root policy.
