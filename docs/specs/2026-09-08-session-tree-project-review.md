# 项目会话树方案评审与替代落地建议

日期：2026-09-08。状态：评审建议，尚未由产品负责人采纳；不是实施完成记录。

评审对象：[原提案](../design/session-tree-project-proposal.md)。依据当前工作区代码、Pi 0.84.2 随包源码及同版本官方文档。工作区已有其他未提交改动，本评审不将它们视为本次交付，也不修改它们。

## 结论

建议采纳「对话路线 / 工作区 / 文件撤销」的分层，但调整问题优先级与实施顺序。原案可以作为方向说明，尚不足以直接进入完整实施。

最重要的修改：

1. 把「所有入口的对话上下文与当前文件状态保持可解释」作为首要缺口；把「尚未使用 Pi 热切树」作为待验证的运行时改进。
2. P0 扩展到编辑分支、失败重试、历史节点续写的统一处理，不能只覆盖已有分支间切换。
3. 独立探索先复用关联会话与 worktree 能力，一个工作会话固定一份工作目录；不在第一版中让同一会话随对话路线更换目录。
4. 顺序改为：**加强版 P0 → 简化版 P3 → 收敛版 P1 → 有门槛的 P2**。Pi JSONL 辅助存储继续独立试验。

这保留了同会话探索，也更早解决真实的并行改代码问题。

## 1. 原案中成立的判断

- 产品已经有会话树；项目与普通会话共用 Host 分支能力。「项目没有树」确实不是准确的问题定义。
- Pi `/tree` 是同场换上下文路线，不会自动回滚工作区。用户消息选择后回到父节点并填入编辑器、非用户节点选择后从该节点继续的描述基本准确。[Pi 0.84.2 sessions.md](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/docs/sessions.md)
- 三层的职责应当分开：对话树管理历史和上下文，工作副本管理仓库文件隔离，撤销管理可验证的文件变更。后台进程、外部服务和权限也不应随对话指针被理解为已恢复。
- 不默认每次编辑都创建 worktree，不把切树做成自动回滚，产品转录继续作为持久权威，都合理。
- 项目成功轮的「重新生成」仍然暴露：当前 `chat-thread.tsx` 创建回调时没有限定 Conversation，`chat-message-row.tsx` 的展示条件也没有该限定。原案这一代码事实成立，尽管 ADR 0064 已写了相反的产品意图。

## 2. 必须先修改的设计与现状判断

### 2.1 使用 Pi.branch 不是产品功能成立的必要条件

原案 §1.3 将「中长期必须用上 Pi 切树」写入成功标准，混合了用户结果和实现手段。

重建运行时后，模型收到当前有效路径，本身可以正确实现树语义。现有重放也不是只拼接气泡文字：`createSeededPiSessionManager` 能重放原生 assistant/toolResult 与压缩种子。另一方面，原生条目截断、文字退化和上下文预算确实可能产生保真差异，需要单独验证。

建议成功标准改为：**无论冷热激活、SDK/RPC 或不同客户端，继续执行时均遵守同一套路径、压缩、附件及工具配对规则；退化行为可观察；切换延迟可接受。** 原生热切树可以实现这个标准，但不是唯一方法。

应先记录现有切换与下一次激活耗时、内存、回放保真缺口，再决定 P2 是否值得主线投入。没有实测证据，不能把「没有调用某个 API」直接等同为结构性缺陷。

依据：`packages/agent-host/src/seeded-pi-session.ts:42`、`packages/session/src/build-replay-seed.ts:26`、`packages/host-runtime/src/cold-activation-seed.ts:17`。

### 2.2 P0 漏掉了最容易造成误解的入口

当前几条路径的处理并不一致：

| 入口 | 当前代码行为 | 评审意见 |
|---|---|---|
| 切到已有兄弟路线 | 检查离开路径的写操作，必要时确认；记录下一轮校准 | 有基础，但不能代表所有探索入口已经覆盖 |
| 编辑历史提问 / 开分支再发送 | `rebaseForBranchPrompt` 直接重建运行时并移到父节点，没有相同的写操作确认与校准 | P0 首先补齐这一入口；否则主验收路径本身绕过保护 |
| 失败重试 | 可确认后删除旧回答子树，再从同一用户消息继续 | 失败可能发生在若干次工具写入之后，不能将其当作未执行过 |
| 成功回答再生成 | 保留旧回答兄弟，当前 Host 路径不走重试删除的写确认 | 关掉项目端默认入口合理；底层上下文处理仍需一致 |

校准目前存于进程内 `Map`，注入前即取出删除；切换后 Host 重启会失去尚未注入的信息。它只在检测到离开路线的写操作时安排，不能将其描述成每次切换都校验了完整磁盘状态。

建议让 Host 统一计算一次路线转换：源路径、目标路径、被离开的执行记录、当前工作区事实及是否需确认。编辑分支、节点续写、切换、重试复用该流程。切换记录与待应用校准应可在 Host 重启后恢复；持久化成功后才算消费，不能只依靠内存标记。

失败重试可以保持一条用户提问，但应保留可追溯的尝试和已发生的副作用。复用现有 Run / attempt 记录，UI 折叠失败过程；不要通过删除唯一的工具执行证据制造「干净重跑」的印象。新上下文须处理已完成动作与未闭合工具调用的区别，不能自动重复全部工具。

写入判定也应区分「已观察到写入」「未观察到写入」「信息不足」。工具记录、Git 状态、模型摘要各自只能提供一部分事实；脚本、MCP、其他会话和人工修改可能不在当前路线记录里。General 会话也有工具与可写目录，不能把 Conversation 标签当作没有副作用的保证。

依据：`packages/host-runtime/src/commands/session-prompt-rebase.ts:35`、同文件 `:71`；`packages/host-runtime/src/commands/session-branch-commands.ts:118`；`packages/host-runtime/src/commands/branch-calibration.ts:78`；`packages/contracts/src/workspace-writes.ts`。

### 2.3 P1 不是仅把分叉列表画成树

当前 `switchActiveBranch(targetMessageId)` 实际会选择目标子树中 sequence 最新的无子节点，不会停在任意指定历史消息。`listBranchPoints` 返回的也是活跃路径上的分叉点，无法直接提供所有离线路线内的节点。

所以 P1 至少包含新的 Host 导航语义与有界树查询，不能只复用现有命令而调整 UI。

建议第一版提供：

- 浏览或预览历史：设备本地选择，不移动共享执行叶子，不打断另一客户端的工作。
- 编辑某次提问：先填充本地草稿，发送时才由 Host 原子地创建新路线。
- 从此继续：明确提交目标节点及预期 revision，Host 在无运行冲突时才改变共享执行路径。过期客户端需刷新，不能沿错误路线继续。
- 初期只允许从完整用户轮或完成的助手轮边界继续。工具节点可查看定位；任意工具节点续写等证明工具调用/结果配对安全后再开放。

Pi 的单终端交互值得参考，但直接照搬「浏览时移动共享叶子」不适合 piwin 的多端 Host。结构化树可以折叠工具过程、按需加载，无须把每条原生内部记录都放到主导航。

依据：`packages/session/src/transcript-store-branches.ts:258`、`:279`、`:315`；`packages/contracts/src/session-branches.ts`。

### 2.4 P2 应以完整导航协议为单位，不能直接调用底层 branch

Pi 0.84.2 中，`SessionManager.branch()` 只验证节点并修改 `leafId`；`branchWithSummary()` 接收已经生成的摘要，并不会自行调用模型。

真正的 `AgentSession.navigateTree()` 还会检查运行状态、处理摘要及取消、调用扩展钩子、应用节点选择规则，并用 `buildSessionContext()` 更新 Agent 消息。只移动 SessionManager 指针可能造成产品库和 Pi 树均已切换，而模型仍使用旧消息。[Pi 0.84.2 agent-session.ts](https://github.com/earendil-works/pi/blob/v0.84.2/packages/coding-agent/src/core/agent-session.ts)

若做 P2，建议定义与 Pi 无关的适配器导航契约，由 `agent-host` 封装公开的完整导航入口；Host 继续拥有准入、Run、持久化与 Push。SDK 和 piwin 自有 RPC worker 同步实现，不让 UI 或 session 包接触 Pi API。

映射需要解决的不是简单的一对一 ID 表：

1. 一个产品回答可关联多个原生条目；工具结果通过 `responseMessageId` 附到回答。映射应描述产品节点对应的原生区间和允许继续的位置。
2. 冷重建只播入当前有界路径，历史兄弟节点未必在热内存树中。导航到不存在的目标时，需要确定地补建或冷重建。
3. Pi 分支摘要、压缩边界、扩展上下文必须有可持久化的产品侧记录；仅留在热树会导致重启后变义。用户应能明确选择是否带走旧路经验，避免一次希望独立比较的探索被旧路摘要污染。
4. 映射应按 Host 的 `runtimeGenerationId` 管理，不能以「同一次桌面进程」作为验收边界。Host 可远程运行，也会主动回收空闲 runtime。
5. 导航被扩展取消、摘要失败、worker 崩溃或产品写入失败时，必须有明确的提交协议。期间禁止 prompt；状态不一致就让 runtime 失效，从产品权威重建后才能继续。

「漂移则回退」只在发送下一次模型请求前能发现漂移时成立；需要可执行的上下文规范化比较，不能只检查两个叶子 ID 相等。

依据：`packages/agent-host/src/native-context-event-map.ts:9`、`:47`；`packages/host-runtime/src/cold-activation-seed.ts:17`；Pi 随包 `dist/core/session-manager.js:1034` 与 `dist/core/agent-session.js:2306`。

### 2.5 P3 的最大问题是起点与执行归属

原案将「路线绑定工作副本，切路线时一起换目录」写得过轻。现有 Session/Run、工具、子代理、终端、权限和配置加载都需要明确的执行归属，修改一个 cwd 字段不足以实现完整切换。一个共享 active leaf 也不能同时支撑 A、B 两条路线各自运行。

更根本的是新工作副本从哪里开始：

| 文件起点 | 真实语义 | 首版建议 |
|---|---|---|
| 明确的 Git commit | 从该提交创建独立目录，不带当前未提交修改 | 首选，显示实际 commit |
| 创建时的当前工作区 | 包含创建时捕获的修改；不是历史提问时的文件状态 | 后续加显式快照，说明 staged / unstaged / untracked / ignored 的范围 |
| 所选历史消息发生时的文件 | 需要那一时刻的可靠完整检查点或等价可验证重建 | 没有证据就不提供此选项 |

`git worktree add` 不能凭一条旧消息恢复当时未提交的代码。当前 `createWorktree` 基于 `baseRef`，默认 HEAD；可复用 Git 执行能力，但现有 helper 还带 subagent 命名和所有权假设，需先抽出通用责任。[Git worktree 文档](https://git-scm.com/docs/git-worktree)

第一版采用 **关联的新会话 + 固定 worktree + 明确 baseCommit** 更稳妥。源会话保存原路线，新会话沿用选中历史前缀并带来源链接；UI 可以按探索关系集中展示，但需显示它是独立会话与目录。已有的产品 Fork lineage 足以承接，不必创建一个新的顶层任务领域，更不能复用 subagent 父子关系。

这会增加关联会话数量，但避免把运行、权限、目录生命周期都升级成「会话内每条路线一套」。若产品未来明确要求同一 sessionId 内多目录并行，再单独设计路线级执行归属。

还需定义非 Git 项目的降级、工作副本创建失败的清理、保留与显式删除、以及独立修改如何查看/整合。隔离的是仓库工作文件，并不代表工具的外部副作用或 OS 权限被隔离。

依据：`packages/git/src/worktree.ts:57`；`docs/specs/session-fork-product-adaptation.md`；`packages/host-runtime/src/turn-changes/coordinator.ts`。

### 2.6 现成能力需要标明边界

- 「切换前列出旧路线修改的文件」当前确认弹窗已实现；P0 应写成统一覆盖并改善解释，而不是新增文件列表。
- 「先暂存再切换」当前是客户端先调用工作区 Git stash，再发分支切换命令。它没有将 stash 与某条路线绑定，也不是一个原子的路线快照操作。不能描述成已保存该路线的文件版本；在多人/多会话共享工作区时，其影响范围尤其需要明确。
- 文件撤销已有 `turn-changes` 的采集、对象存储和部分 undo/redo 命令基础。应盘点复用并验证完整度，不能视为从零建设，也不能因代码存在就认定已完整交付。当前 command handler 的其他若干能力仍返回 unsupported。

依据：`apps/desktop/src/branch-switch-confirm-dialog.tsx`；`apps/desktop/src/hooks/use-branch-actions.ts:525`；`packages/host-runtime/src/commands/turn-change-commands.ts`。

## 3. 建议的交付顺序

| 阶段 | 用户结果 | 必要验收 |
|---|---|---|
| 加强版 P0：统一切换/重试 | 每个探索入口都解释当前文件状态；失败记录不会掩盖已执行的动作 | 编辑分支、切换、部分成功后失败重试、Host 重启待校准，均覆盖；取消不改变当前路线 |
| 简化版 P3：独立探索 | 从明确提交创建关联会话与 worktree，A/B 可以分别运行和查看 | 源目录不变；新目录起点可验证；失败清理和显式保留有效；CLI/多端共享 Host 命令 |
| 收敛版 P1：浏览与继续 | 可查整棵对话树，在安全轮边界明确继续 | 预览不改变另一客户端执行路径；revision 冲突不会沿错误路线发送；工具调用保持闭合 |
| 有门槛的 P2：热导航 | 有实测收益时减少 runtime 重建，保持上下文规则一致 | SDK/RPC 同一矩阵；摘要取消、压缩、冷目标、回收、重启、映射故障均能正确处理 |

如果近期最强反馈是「找不到某一条旧回复」而非并行改代码，可以交换 P1 与简化版 P3；没有理由仅因为 Pi.branch 更接近原生 API 就让 P2 阻塞工作区能力。

若只做两个阶段，选择加强版 P0 与简化版 P3，明确完整节点导航尚未交付，不宣称全部成功标准已经满足。

## 4. 对原案七个评阅问题的直接回答

1. **问题定义是否准确？** 现象与「已有树」准确；B 是核心用户问题，A 应拆成上下文保真、导航能力与性能，不能合并为「不用 Pi.branch 就没做对」。
2. **Pi 参照是否合理？** 合理，文件不回滚的判断正确；P2 混淆了底层树存储方法与完整运行时导航。
3. **三层是否清晰？** 清晰，保留；再明确尝试/Run、当前文件起点与运行状态的归属，无须把它们包装成第四套用户树。
4. **阶段顺序是否合理？** 建议 P0 → 简化 P3 → 收敛 P1 → 有门槛 P2，P1/P3 可按实际反馈交换。
5. **最大风险？** 产品层面是 P3 的历史起点承诺与运行归属；技术层面是 P2 的上下文一致性及提交失败处理。眼前最直接的遗漏是 P0 没覆盖编辑新版本的真实执行路径。
6. **只做两个阶段？** 加强 P0 与简化 P3。
7. **更优替代？** 保留共享目录内的同会话树，独立探索使用关联新会话与固定目录；不建议所有探索强制新会话，也不建议第一版把所有运行状态下沉到路线级。
