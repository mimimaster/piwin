# 工具调用错误：会话诊断与修复建议

- 日期：2026-08-31
- 状态：诊断完成；解决建议待实施，本文不代表修复已完成
- 样本会话：`session-mth2b6mx-l0ee5jsw`
- 样本任务：修复 Composer 草稿附件在发送前被提前释放
- 调查方式：只读检查会话数据库、工具原始结果和当前源码；未重跑样本命令、未干预会话
- 时间口径：下文时间均为北京时间；消息时间用于定位，不代表工具精确开始或结束时间

## 1. 结论

这轮工具报错不是单一问题，不能统一归为“正常试错”，也不能理解为“piwin 崩溃”。

1. **正常的开发反馈**：修复前复现测试失败；模型生成的脚本语法有误；修改后的类型检查发现遗漏。这些错误可以通过阅读结果、调整实现、重新验证来恢复。
2. **执行环境不一致**：项目会话中的命令实际从产品数据目录启动，运行环境又缺少开发工具所在的 PATH，造成了本可避免的失败。
3. **文件写入边界不一致**：写入实际项目内的文件被报为越出仓库。这需要校准会话作用域与工具使用的根目录，不能简单关闭路径检查。
4. **错误信息传递不完整**：部分失败结果只剩命令文本，没有真正的诊断输出；大段错误又被界面从开头截断，增加了模型恢复和用户理解的成本。

建议优先修复“执行上下文一致性”和“失败结果保真”，再优化错误展示。目标不是减少红色卡片，而是让每次失败都能被准确判断，并支持安全恢复。

## 3. 问题描述与定位

### P1：会话项目与工具执行上下文不一致

**证据：**

- 会话元数据中的 `project_path` 是 `/Volumes/BigDisk/Projects/Projects/piwin`。
- 会话内消息 16 的路径探测确认它是指向 `/Users/yorickjue/Developer/piwin` 的软链接。
- 消息 13 的 `pwd` 返回 `/Users/yorickjue/.piwin`。
- 元数据中的 `scope_json` 与 `working_directory` 在调查快照中均为空。
- `write_file` 分别报告 `../../Developer/piwin/...` 和 `../../../../Volumes/BigDisk/...` 越出仓库。

**影响：** 相对路径命令失效、项目内写入被拒绝，模型需要反复探测路径，并转向其他执行方式。错误根目录还会影响权限与变更追踪的作用域。

**定位与不确定性：**

- `build-session-host-tools.ts` 使用 `options.projectPath ?? rootDir ?? process.cwd()` 决定文件和 Bash 工具目录。
- `host-filesystem-tools.ts` 的写入路径会相对于 `turnChange.workspaceRoot` 做仓库边界检查。
- 运行结果已证实目录不一致，但尚未定位到具体的参数丢失调用点。旧会话恢复、作用域归一化、工具 generation 创建与变更追踪根目录的传递链需要用回归测试进一步核实。
- 不能仅归因于软链接：样本使用真实路径和软链接路径都失败。
- `path escapes repository` 来自仓库路径校验，不是已经证实的操作系统沙箱拒绝。

### P2：Host 子进程缺少开发工具运行环境

**证据：** 消息 21 返回 `PATH=/usr/bin:/bin:/usr/sbin:/sbin`，同时找到 `/opt/homebrew/bin/pnpm`，但当前环境无法解析 Node。之后显式补充 PATH，测试可以启动。

**影响：** 用户机器已安装的工具在 Agent 中不可用；每次调用都依赖模型手工补 PATH，增加不必要的环境猜测。

**边界：** GUI 启动环境差异是可能来源，但本次只确认了传给工具的环境内容，没有证明是某一段 Tauri 启动代码导致。

### P3：失败结果丢失 stdout、退出码等信息

**证据：** 消息 42、44 的原始工具结果只包含 `Command failed` 和命令，具体 TypeScript 错误没有进入结果。消息 45 改为保存并读取输出后，才看见：

`TS6133: 'createSavedMediaResponse' is declared but its value is never read.`

**当前链路：**

1. `host-filesystem-tools.ts` 通过 `execAsync` 执行命令，成功时返回 stdout/stderr。
2. 失败时异常进入 `host-tool-execution-router.ts`。
3. Router 使用 `formatError(error)`；`piwin-error.ts` 对普通 Error 只保留 `.message`。
4. 异常对象上的 stdout、退出码、signal 等结构化字段没有被带入工具结果。写到 stdout 的诊断可能因此消失。

**影响：** 用户只知道“失败了”，模型也可能无法获取原因。它必须额外重跑命令才能找回证据。对于有副作用的命令，这种重跑并不安全。

### P4：展示截断与失败摘要遮蔽根因

`agent-host/src/tool-presentation.ts` 当前将展示输出限制为前 8,000 字符，并用开头文本构造最多 120 字符的普通错误摘要。长命令本身可能已经占满摘要，真正的错误位于后面。

**影响：** 命令被重复显示，关键诊断和结尾汇总容易消失。样本中原始工具消息比 UI 结果长，不能把“界面截断”直接解释成“模型也只收到这部分”。这与 P3 在结果构造时丢失信息是两个不同问题。

### P5：工具调用状态不等于整体验证结论

消息 45 与 47 的工具状态是 done，但输出明确包含 `EXIT:1`。原因是脚本在失败命令之后继续打印日志，最终脚本正常退出。

另外，复合命令失败也不表示前面的操作没有发生。样本消息 20 在找不到 pnpm 之前执行了文件恢复命令；不能因为整条调用标记失败就假定没有文件副作用。

因此，不应仅按红/绿卡片数量评估任务质量，也不应自动把失败命令原样重跑。

## 4. 其他 coding agent 的可借鉴做法

以下依据 2026-08-31 查阅的官方文档，不代表所有版本或界面的行为完全一致。

| 产品 | 文档明确的做法 | 对 piwin 的启示 |
|---|---|---|
| Codex | 命令记录包含 cwd、status、输出、exitCode、durationMs；支持输出增量。独立命令接口返回 stdout、stderr、exitCode | 执行结果应保留结构化事实，而不是压成一句异常文本 |
| Claude Code | 读取失败结果、修复、重新测试属于正常循环；超长失败输出保留头尾；部分已识别的搜索/比较命令退出码 1 可以是有效结果 | 失败不必终止整轮；保留可诊断内容，并只对语义明确的情况做分类 |
| Gemini CLI | Shell 返回命令、目录、stdout/stderr 和退出码 | 模型和用户应得到足够信息来区分环境、业务与执行故障 |

来源：[Codex App Server](https://learn.chatgpt.com/docs/app-server#items)、[Claude Code 工具输出限制](https://code.claude.com/docs/en/tools-reference#output-limits)、[Claude Code 工作循环](https://code.claude.com/docs/en/how-claude-code-works#the-agentic-loop)、[Gemini CLI Shell](https://geminicli.com/docs/tools/shell/#return-values)。

不建议直接照搬其他产品的字符上限或对所有退出码 1 放行。piwin 应先保证执行事实完整，再按具体工具语义决定如何呈现。

## 5. 解决建议

### 第一步：对齐执行上下文与环境

**负责：`host-runtime` 组合；复用 `session`、`project`、`git`、`process` 已有公共能力。**

1. 在会话恢复与 runtime generation 创建时，归一化 `scope`、项目路径、工作目录及受信任根目录。复用现有旧会话归一化入口，不为 Bash 再造一份规则。
2. 项目会话的文件工具、Bash、权限判断、变更追踪使用同一份解析结果；工具 manifest 与后端会话也应核对一致性。
3. 元数据明确属于项目、但执行根目录无法解析时，应返回可操作的错误，不能静默回落到产品数据目录。真正的 general 会话保留其独立规则，不因提示词出现绝对路径就获得项目信任。
4. 对已有项目根目录统一处理真实路径与软链接别名。新文件的父目录按现有路径安全能力处理，继续阻止真正越界及通过软链接逃逸的写入；不宣称消除了所有文件系统竞态。
5. 在 Host 启动/执行环境层解析开发工具 PATH，保留显式配置与远程 Host 环境。不要修改用户 shell 配置、不要每条命令启动交互 shell，也不要在跨平台代码里写死一条 Homebrew 路径。
6. 增加有界诊断：仅记录会话/generation 标识、解析后的执行目录及必要工具可用性；不记录完整环境变量或密钥。

**前置验证：** 先用旧元数据、软链接路径及冷启动恢复构造失败用例，再确定最小修复点。不能只在最外层强加 `cd` 掩盖参数传递问题。

### 第二步：保留结构化执行结果

**负责：`contracts` 定义；`process` 承载进程 I/O；`host-runtime` 接入原有工具路径；`agent-host` 做 SDK/RPC 映射。**

1. 基于现有 `ToolResult`、`ToolResultDetails`、`ToolPresentation.exitCode` 做增量扩展，不新增平行工具协议。
2. 在具名的命令执行结果中保留：cwd、退出码或 signal、耗时、stdout/stderr 的有界片段、截断信息，以及超时/取消/启动失败等明确原因。字段名在 contracts 阶段最终确定。
3. 非零退出按当前失败语义返回 `execution-failed`，但必须带回诊断；沿用现有 `details.reason` 表达超时等原因，不为本次修复重做错误码体系。
4. 在执行器/进程边界识别并转换已知异常，而不是让全局 `formatError` 猜测所有错误形状。
5. SDK、RPC、实时推送、历史恢复都消费同一份结构化结果。模型可见结果也必须包含退出事实和诊断，不能只补 UI。
6. 取消、超时和输出采集上限分开表达；没有证据时退出码保持未知，不能伪造。调用超时不代表进程一定停止，也不代表未产生副作用。

**最小切片：** 先在现有执行链上修复失败结果保真并补回归测试。如果需要替换进程执行方式，先检查 `@piwin/process` 的现有能力；不得建立第二套会话或 Job 执行权威。

### 第三步：分离日志保留与摘要展示

**负责：Host 管理日志；contracts 提供引用；Desktop/CLI 消费公共接口。**

1. 短输出内联；长输出采用有界的头尾片段，让尾部失败汇总有机会保留。stdout/stderr 都应有预算，避免一种输出完全挤掉另一种。
2. 按需增加 Host 管理的日志读取能力。检查现有日志/溢出存储是否可复用；新存储应绑定 session/run/toolCall，设单次和总量上限、生命周期与清理规则。
3. “查看完整输出”只在完整日志确实保留时出现；若采集本身已丢弃内容，应明确标注不可恢复，不能靠重跑伪装成读取日志。
4. 日志引用需做会话归属与路径校验，远程客户端通过 Host 读取，不能直接依赖 Host 绝对路径。落盘/投影前执行明确的敏感信息处理策略，不能假定普通正则可以识别所有秘密。
5. 超长输出只应影响输出预算；若因硬资源限制停止采集或终止进程，应使用独立原因说明。不要将展示截断误标为执行失败。

### 第四步：改进错误呈现与恢复策略

**负责：`agent-host` 归一化展示事实；Desktop 使用 `ui-kit`；CLI 提供对应文本信息。**

- 优先呈现简短原因，例如“找不到 pnpm”“类型检查失败：未使用的导入”，命令只保留一个明确的查看入口。
- 可以可靠识别时给出失败数量；无法识别时展示退出事实和输出片段，不根据文字猜出“20 个失败”等结构化结论。
- `truncated` 保持独立提示；工具失败保持该次历史事实，不因后续重试成功而修改旧结果。
- 单次工具失败不直接触发整轮任务失败。继续遵循现有 Pi outcome → Host Run 终态权威，避免新增 Host 自动重试循环。
- 搜索无匹配等良性非零退出，只在工具语义明确、解析可靠时归类。首个修复切片不需要引入通用 shell 语义分类器。
- 权限/路径拒绝不能自动改用另一工具绕过。应先区分配置不一致与真实拒绝；真实授权不足需要用户决定。
- 对测试/类型错误，由模型读取证据后修复再验证；对可能有副作用的失败，先检查已发生的变化，不原样自动重放。维持现有调用去重和 late-settlement 约束。

## 6. 实施顺序与验收

建议按关注点分开提交；本次文档不授权开始实施。

| 阶段 | 交付 | 必须通过的验证 |
|---|---|---|
| A：复现与上下文修复 | 明确参数丢失点，统一作用域/根目录；修复环境解析 | 旧会话恢复、项目软链接、general 会话、多项目并发、精简 PATH 启动 |
| B：结果保真 | 增量 contracts 与命令结果适配 | 非零退出仍保留 stdout/stderr/退出码；超时、取消、启动失败可区分；SDK/RPC 一致 |
| C：长输出与展示 | 有界头尾、日志引用、原因摘要 | 超长输出不会撑爆传输；历史恢复一致；查看日志不重跑命令；敏感内容不泄露 |

关键回归用例：

1. 项目会话首条 `pwd` 返回正确项目目录；general 会话不意外继承项目权限。
2. 恢复 `scope`/`workingDirectory` 缺失的旧项目会话，文件、Bash、变更追踪根目录一致。
3. 项目软链接与真实路径按同一规则处理；真正越界和软链接逃逸仍被拒绝。
4. Shell 仅向 stdout 输出诊断并退出 1，模型和 UI 都能看到诊断与退出码；仅 stderr、两者都有、无输出的失败同样覆盖。
5. 输出包含数万字符、结尾才有失败汇总时，摘要或尾部片段仍能支持诊断；展示截断不改变成功/失败状态。
6. 取消、deadline、进程启动失败与资源上限分别验证，不伪造终止或退出码。
7. 日志分页读取有归属校验、长度限制和生命周期；过期日志返回明确状态，不自动重跑。
8. 复合命令中子步骤失败但最终退出 0，不把整个输出解释为“全部检查通过”；失败也不表示前置副作用已回滚。
9. 后续工具恢复成功，原错误仍保留，但不会仅因为存在历史 tool error 就判整轮失败。
10. 定向测试通过与全量测试未通过分开报告；“既有失败”需有对照证据，否则写明未确认归因。

完成标准：相关包测试通过；`pnpm typecheck` 通过或明确记录仍未解决的外部阻塞；公开导出与协议兼容性核对；Desktop/CLI 和 SDK/RPC 做对应冒烟；修改源码遵循职责拆分与行数上限。涉及已接受行为变化时，同步更新相关 ADR/spec，不把提案提前写成已落地事实。
