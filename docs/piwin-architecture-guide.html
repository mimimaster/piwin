这条分支到底干了什么？

它不是单纯增加几个功能，而是在重新分配“谁有权管理什么”。最终目标是：每一类生命周期只有一个负责人，取消、并行、清理和重载都不再由多套代码同时决定。

先看结论

从“很多人都能管”变成“每件事只有一个管家”

当前分支的真实状态：新模块已经搭起，但旧路径还没有全部拆除。

Host Runtime

产品组合总管

当前已建立，仍需收口

它负责什么

读取设置、项目权限、模型和资源，然后决定一次操作能不能做、应该怎么做。

它不负责什么

它不直接代替 Pi 内核执行，也不应该让 Desktop 自己拼装产品策略。

用户得到什么

Desktop 和 CLI 走同一套决策，权限、工具和模型行为一致。

二、这条分支实际改了什么

不要把下面的“目标”误看成“已经全部完成”。当前分支的关键事实是：新地基已经开始替换旧路径，但收口还没完成。

把产品组合集中到 Host Runtime

让 Desktop 和 CLI 不再各自决定 Agent 怎么创建、怎么授权、怎么执行。

之前入口各自拼装行为，容易出现不同步。
现在Host Runtime 已成为产品组合根，旧入口还要继续封死。

把 Process 语义收敛成 Job

所有 dev server、watcher、build 等非交互式系统进程由同一套生命周期管理。

之前ProcessRegistry、ManagedProcess 等兼容模型混在一起。
现在JobController 和 job/* IPC 已建立，兼容层仍需删除。

把 Run 变成任务生命周期中心

一次聊天、计划或子任务都要有明确的开始、取消、等待和 terminal 状态。

之前RunRegistry、ActiveRunRegistry、session guard 都可能影响状态。
现在RunRegistry 基础已存在，前台 authority 还没有完全收口。

把并行子代理集中到 Orchestrator

统一处理并发额度、依赖、失败传播、取消和 worktree 集成。

之前现代调度器和 Desktop / Plan 旧入口同时存在。
现在SubagentOrchestrator 已建立，但所有入口还要迁移到它。

为并行写入加入安全合并边界

每个写代码的 Agent 使用独立 worktree，最终通过串行合并回主项目。

之前旧路径可能直接操作主分支或并发合并。
现在IntegrationCoordinator 方向已明确，旧合并路径仍需移除。

把 Pi Worker 变成可追踪的执行边界

Worker 不应该拥有产品权限或 OS 副作用，只负责 Pi 会话执行和事件传递。

之前前台 RPC 和子代理 Supervisor 各自管理 Worker。
现在Supervisor 方向已建立，但 Worker authority 还要统一。

三、用流程看懂系统怎么工作

架构图回答“谁负责什么”；下面的流程图回答“一个用户动作到底怎么走”。

例子：用户在 Desktop 输入“帮我修这个 bug”。重点是：UI 不直接碰 Pi，Host 先创建 Run，再由 backend 执行。

1

用户输入

Desktop / CLI

收集文本、图片和当前 Session 信息，只发送一个产品命令。

HostCommand
2

准备能力

Host Runtime

读取设置、权限、模型、工具和项目，生成 Session Blueprint。

Blueprint
3

登记任务

RunRegistry

创建一个真实 Run，立即返回 runId，状态通过 HostPush 更新。

runId + run/updated
4

执行 Pi

WorkerSupervisor → Pi

把 prompt 发给对应 Session / generation 的 Pi backend，工具调用回到 Host。

agent/event
5

收尾展示

RunRegistry → UI

等 agent、tool 和关联 Job 都收尾后，Run 才进入 terminal，界面展示最终结果。

run/terminal
为什么要有 RunRegistry？因为“Pi 回答结束”不一定代表“整个产品动作结束”：它可能还启动了 Job，或者还有子任务需要清理。

例子：用户让系统执行一个包含 5 个步骤的计划。重点是：并行调度和代码合并不能由 UI 或某个子 Session 私自决定。

1

创建计划 Run

Host Runtime + RunRegistry

先有一个 plan-execution Run，所有 batch 和 child Run 都挂在它下面。

父 Run
2

安排并发

SubagentOrchestrator

检查依赖、容量和 dirty-base 策略，决定哪些任务可以同时开始。

taskRun 树
3

隔离执行

Workspace + WorkerSupervisor

每个写入任务得到独立 worktree 和对应 Worker，事件带 taskId / runId。

worktree + Worker
4

串行集成

IntegrationCoordinator

任务完成后进入集成队列，用三方合并处理；冲突就保留现场，不自动覆盖。

merged / conflict
5

汇总结束

RunRegistry

所有子 Run 和 integration job 都 terminal 后，父计划 Run 才结束。

Plan summary
dirty base 不是静默拒绝，也不是静默 bypass。目标是通过 ask 机制让用户选择继续、先 commit/stash，或取消。

例子：用户点击“停止”。重点是：停止是一个有顺序的收尾事务，不是把 UI 上的 loading 改成 false。

1

用户发起停止

Desktop / CLI

发送 cancel 命令，不能自己直接 kill 某个未知进程。

run/cancel
2

关闭新工作

RunRegistry

关闭 admission，进入 cancelling，不再接受新的 child Run。

cancelling
3

从叶子开始取消

RunRegistry → Workers

先取消子任务和 Pi prompt，再等待它们报告收尾。

abort / join
4

清理系统进程

JobController

根据 ownerRunId 停止属于这次 Run 的 dev server、watcher 和 build。

job/stop
5

发布最终状态

RunRegistry → UI

后代都 terminal 后，父 Run 才 terminal；UI 得到真实而不是猜测的状态。

run/terminal
同一个原则也适用于 Runtime reload：真正的 reload 必须是创建 candidate、重建 backend、原子替换 active generation 的事务。未完成前不能伪装成成功。

最后，用产品语言总结

这条分支正在把 piwin 从“功能能跑，但多个地方都在管理”改成“每个动作都有清晰的产品负责人”。当前已经完成的是地基和部分迁移；剩下最重要的工作是删除旧 authority，而不是再增加一套新机制。

Host Runtime：决定能不能做、应该怎么做
RunRegistry：决定任务何时开始、取消、结束
JobController：决定系统进程如何启动、日志、停止
Orchestrator / Worker：分别负责调度和真正执行
